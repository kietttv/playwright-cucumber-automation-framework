# Failure report format

`test-script-generator` and `test-script-healer` write these reports, and `bugs-reporter` reads and updates them. It's framework-agnostic: the folder comes from the **Failure reports** row of the Project profile in `AGENTS.md` (or `CLAUDE.md`).

## Location and naming

- One report per generator or healer run (or batch): `<failure reports folder>/<TICKET-KEY>_<spec-file-name>_<YYYY-MM-DD>.md`, e.g. `PROJ-101_orderslayoutcards_2026-10-01.md`. If one already exists for the same ticket, spec and day, update it instead of creating a second.
- **Evidence:** copy each app failure's artefacts (screenshot, video recording, error-context file, and trace if there is one) into `<report name>/<case ID>/` next to the report. The test runner overwrites its results folder on the next run, so the report must not point there.
- Write a report only when there's at least one app failure. If there are none, say so in the final report and skip the file.

## What counts as an app failure

Only **expected failures** (the generator) or **real app bugs and design mismatches** (the healer): the app's behaviour or wording differs from the AC or design. Never known bugs already tagged with a bug key. Never list script failures, flaky tests, environment problems or TBC tests as app failures; they go in the "Not bugs" section for reference only.

## Template

```markdown
# Failure report: <TICKET-KEY> – <ticket summary>

| Field | Value |
|---|---|
| Story | <TICKET-KEY> |
| Test-case doc | <path to the suite doc> |
| Spec | <path to the test file> |
| Environment | <environment name from the profile, e.g. QA> |
| Run date | <YYYY-MM-DD HH:mm, with time zone> |
| App version | <build, version or commit if visible in the app or API; otherwise "unknown"> |
| Generated by | test-script-generator or test-script-healer |

## App failures (candidate bugs)

| Case ID | Title | Priority | Group | Expected (source) | Actual | Evidence | Bug |
|---|---|---|---|---|---|---|---|
| TC-1918 | Verify card 1 label | High | A | "Active orders" (design: specs/orders.md §5) | "Orders" | TC-1918/ | |

## Suspected groups (shared root cause)

- **A:** <one line: what's wrong, where>. Cases: TC-1918, TC-1920.

## Not bugs (reference only)

- **Real failures (script):** <case IDs, one-line error>
- **Skipped (TBC):** <case IDs and gap>
- **Environment issues:** <case IDs, one line>
```

## Column rules

- **Expected (source):** the expected result **and where it comes from** (AC number, design spec section or prototype screen), never the app's own code.
- **Actual:** what the run showed, quoted exactly for text.
- **Evidence:** the evidence folder for that case, relative to the report.
- **Group:** the generator's best guess. `bugs-reporter` reviews and may regroup.
- **Bug:** left empty by the generator. `bugs-reporter` fills it in with the new ticket key, `dup of <KEY>` (an existing ticket), or `not raised: <reason>`.
- No secrets, credentials, env URLs with tokens, or real personal data anywhere in the report.
